01 / CONCEPT

Copilotにブラウザの手を渡す

Copilotが目的を解釈し、MCPでツールを呼び、Playwrightが画面を操作する。結果を観察しながら、次の一手を決める仕組みです。

目的と期待値を定義開発者 ＋ GitHub Copilot

計画・対象・操作範囲を共有する

接続の規約MCP

ツールの一覧・引数・結果を受け渡す

ブラウザ操作を提供Playwright MCP server

移動・構造取得・入力・クリック・証跡

対象のWebアプリブラウザ

観測した結果をCopilotに返す

MCPはModel Context Protocolの略で、AIクライアントとツール提供側をつなぐ規約です。Playwright MCPはブラウザ自動操作を提供するサーバー、GitHub Copilotはそのツールを使う側です。MCPの導入だけでアプリの仕様を理解するわけではありません。

構成要素役割開発者が確かめること
GitHub Copilot目的に沿ってツールやコード変更を選ぶ期待値と操作範囲が明確か
MCP serverブラウザ操作ツールを公開する意図したサーバーが実際に呼ばれたか
Playwright / ブラウザ操作を実行して状態を返す対象URL・認証・データが正しいか
Playwright Testコード化した期待値を繰り返し検証するassertionが仕様を表しているか

02 / DECISION

MCP・CLI・内蔵ツールを選ぶ

経路向いている使い方判断のポイント
Playwright MCPCopilotから構造を観察しながら段階的に操作MCP設定とツール呼び出しを管理する
CLI ＋ Skills端末を使うAIとコード修正・画面確認を進めるシェル実行環境とスキル配置を整える
VS Code内蔵ブラウザツール追加サーバーなしで日常的な画面確認使用中の環境で利用可能か確認する
Playwright TestPRやCIで同じ確認を繰り返す人が期待値をレビューし、コードへ固定する

本ガイドはPlaywright MCPを使う経路です。接続確認では「Playwright MCPのツールを使う」と明示し、内蔵ブラウザツールやCLIで代用された結果と混同しません。

CLIの追加やSkillsの導入は、MCP利用の必須条件ではありません。Skillsは手順を補う仕組みであり、MCPはツールとの接続を担当します。トークン消費や速度はツール数・出力・ページ規模で変わるため、小さな試験で比較します。

関連ガイド：Playwright CLI＋Skills →

03 / PREPARATION

Windowsの準備と実行場所

VS Code、GitHub Copilotを利用できるアカウント、Node.js、npm/npx、試験用のWebアプリを用意します。公式READMEのNode.js要件は18以上ですが、新規導入にはサポート中のLTS版を使ってください。

PowerShell / 実行環境の確認
node --version
npm --version
npx --version
npx -y @playwright/mcp@latest --help

最後のコマンドはサーバーのオプション確認です。ここで止まるなら、MCP設定より先にnpmレジストリへの接続、プロキシ、Node.jsのPATHを確認します。画面操作はまだ行いません。

環境localhostが指す場所確認すること
Windows上のVS Code・ローカルMCPWindows側TomcatなどのURLをWindowsから開けるか
WSL / Dev Container / SSH先のMCPそのLinux・コンテナ・接続先ブラウザの実行場所、依存ライブラリ、到達URL
Copilotのクラウド実行環境クラウド内社内ネットワークへの接続経路があるか

端末からWebアプリを開けても、MCPが別環境で起動していれば接続できない場合があります。「Copilotの場所」「MCPの場所」「Webサーバーの場所」を区別します。

04 / SETUP

VS CodeにMCPを追加する

2026年11月確認のVS Code公式資料では、選択した実行方式（harness）によって推奨設定先が異なります。まずコマンドパレットから登録し、画面に表示された保存先を確かめます。

  1. VS Codeで対象プロジェクトを開き、Copilotを使うセッションを選択します。
  2. Chat: Open Customizations → MCP Servers → Add Serverを開きます。代わりに MCP: Add Server からも開始できます。
  3. Command (stdio)を選び、下記コマンドを指定します。
  4. サーバーIDを playwright にします。個人利用の案内では Global → Copilot Global を選びます。
  5. 生成されたコマンドと設定を確認し、対象サーバーを起動して最初の呼び出しへ進みます。
登録する起動コマンド
npx -y @playwright/mcp@latest

stdioは、Copilot側が起動したサーバープロセスと標準入出力で通信する方式です。初回のローカル利用では公開ポートを作る必要はありません。

設定先形式使う場面
~/.copilot/mcp-config.jsonmcpServers / type: local現行Copilot向けの個人設定。COPILOT_HOME指定時はその配下
ワークスペース直下 .mcp.jsonmcpServers / type: local対応するCopilot環境でチーム共有。VS Codeの登録導線は実験設定に依存
.vscode/mcp.jsonservers / type: stdio従来のVS Code形式・Local harness向けの互換設定
画面や設定先が違う場合

VS Codeの版・選択中のharness・組織ポリシーで表示が異なります。現行資料では .vscode/mcp.json の登録導線は互換向けとして扱われています。利用中の環境が読む形式を選び、複数の設定先に同じサーバーを重複登録しないようにします。

05 / CONFIGURATION

設定ファイルを読み解く

学習用の設定例では --isolated を付け、ブラウザのプロファイルをメモリ内に保持します。永続プロファイルが既定の構成とは、再起動時の認証状態が異なります。

Copilot形式 / 個人設定 または対応する .mcp.json
{
  "mcpServers": {
    "playwright": {
      "type": "local",
      "command": "npx",
      "args": [
        "-y",
        "@playwright/mcp@latest",
        "--isolated"
      ],
      "tools": [
        "*"
      ]
    }
  }
}
従来の .vscode/mcp.json を使う場合
.vscode/mcp.json / VS Code形式
{
  "servers": {
    "playwright": {
      "type": "stdio",
      "command": "npx",
      "args": [
        "-y",
        "@playwright/mcp@latest",
        "--isolated"
      ]
    }
  }
}

既存の servers オブジェクトに追加してください。既存のサーバー定義をファイルごと置き換えないようにします。

項目意味
commandMCPサーバーを起動するプログラム
argsパッケージ名とオプションを1要素ずつ指定
-ynpxのパッケージ取得確認を省く
@latest導入時点の最新版を取得。チーム運用では検証した版に固定
--isolatedディスクへ永続プロファイルを残さない
tools: [*]Copilot形式で公開ツールを利用対象にする。各操作の承認とは別

導入確認後は、使用したパッケージ版、Node.js、ブラウザ、Copilot・VS Codeの版を記録します。@latest を検証済みの具体的な版に置き換えると、再現性を高められます。

PowerShell / 配布版の確認
npm view @playwright/mcp version
npm view @playwright/mcp engines
# 取得した版を設定の @latest の代わりに指定する

mcpServers と servers は設定形式の違いです。外側のキーだけを機械的に変更せず、type などの対応も確認してください。

06 / HANDS-ON

接続を確かめ、最初の操作へ

最初はタイトルと構造だけ取得する

Copilotへの接続確認プロンプト
Playwright MCPサーバーのツールを使い、
https://demo.playwright.dev/todomvc/ を開いてください。
内蔵ブラウザツールやCLIには切り替えず、使用したMCPツール名を示してください。
ページタイトルと入力欄をsnapshotから報告してください。
ファイル変更やタスク追加はまだ行わないでください。

会話中のツール呼び出しを展開し、Playwright MCPの browser_navigate や browser_snapshot が使われ、実際のページ状態が返っていることを確認します。もっともらしい回答だけでは接続成功と判断しません。

Todoを1件追加して完了にする

Copilotへの操作プロンプト
同じPlaywright MCPのブラウザで続けてください。
1. 最新snapshotでTodoの入力欄を特定する。
2. 「MCPガイドを読む」を1件追加する。
3. 追加された項目が1件あることを確認する。
4. その項目を完了にして、完了状態を確認する。
5. スクリーンショットを保存し、実際の保存先を報告する。
各段階で操作対象と結果を説明し、失敗したらそこで止めて根拠を示してください。
観察最新snapshotから対象を特定操作入力・クリック・キーを実行検証期待状態と画面・ログを照合

タスクを追加できたことと、アプリ全体の試験が完了したことは別です。次は空欄・複数追加・削除など、仕様に沿ったケースを分けます。

07 / OBSERVATION

snapshot・ref・targetの仕組み

snapshotは画面のアクセシビリティ構造をテキストで表します。画像と違い、ボタン・入力欄のroleやラベル、操作に使う参照を読み取れます。

構造の概念例 / 番号は説明用
- textbox "What needs to be done?" [ref=e5]
- listitem [ref=e9]:
  - checkbox "Toggle Todo" [ref=e10]
  - text: MCPガイドを読む
MCPツール呼び出しの例 / シェルコマンドではありません
browser_type {
  "target": "e5",
  "text": "MCPガイドを読む",
  "submit": true
}

browser_snapshot { "depth": 4 }

browser_click { "target": "e10" }

これらはCopilotが呼ぶツールの引数例であり、PowerShellへ貼り付けて実行するコマンドではありません。refは必ず実際の最新snapshotから取得します。再描画やページ移動後に、古い番号を盲目的に使いません。

旧記事と引数名が違う

現行の公式資料では多くの操作が target を受け取ります。古い記事には ref と element を使う例もあります。接続したサーバーが公開する実際のツールスキーマを優先し、新旧の引数を混ぜないでください。

大きな画面では browser_find で必要な文字列を探し、browser_snapshot の target や depth で対象を絞れます。Canvasの描画、色、重なりは構造だけで分からないため、画像やアプリの値と併せて確認します。

09 / COPILOT PRACTICE

計画・実行・修正を分ける

1つの依頼ですべてを任せる前に、調査計画を共有し、再現結果を読んでから修正へ進みます。途中の成果物を明確にすると、人が進捗を監督しやすくなります。

段階1 / 仕様から計画を作る
docs/search-spec.md を読み、検索画面の試験計画を作ってください。
正常検索、0件、空欄、境界値の前提・操作・期待結果を表にしてください。
仕様で決まっていない部分は「要確認」とし、推測で期待値を埋めないでください。
この段階ではブラウザ操作とコード変更は行わないでください。
段階2 / MCPで観測する
計画のケース1だけを、Playwright MCPで実行してください。
対象は http://localhost:8080/ です。
snapshotで対象を確認し、結果・画像・consoleエラーを報告してください。
期待値と観測事実を分け、未実行の項目を明記してください。
コードはまだ修正しないでください。
段階3 / 最小修正を検証する
確認した不具合の原因候補をコードと照合し、最小修正を提案してください。
修正後は同じ操作で再確認し、関連する既存テストも実行してください。
再発防止用のPlaywright Testを追加し、変更内容と試験結果を報告してください。

アプリの仕様は、操作履歴だけで永続的に学習されるとは限りません。docs/ に期待仕様、tests/ にテスト、障害記録に再現条件を残します。観測した現在の動作を、そのまま正しい仕様として固定しないことが大切です。

10 / AUTHENTICATION

認証とブラウザ状態を扱う

方式状態の扱い使いどころ
既定の永続プロファイルブラウザ状態をディスクへ保存専用のテストアカウントで反復作業
--isolatedメモリ内のプロファイル初期状態をそろえる試験
--storage-state保存済みstateから開始ログインを繰り返さず試験
--extension既存Chrome / Edgeへ接続手動ログイン済みタブを使う必要がある場合

isolatedでログインしてstateを残す

まずテストユーザーでログインし、利用可能な場合は --caps=storage と browser_storage_state を使って保存します。その後、次の起動引数で読み込みます。

argsの例 / 実在するstateファイルを指定
[
  "-y", "@playwright/mcp@latest",
  "--isolated",
  "--storage-state", "${workspaceFolder}/playwright/.auth/user.json"
]

上記の ${workspaceFolder} は従来のVS Code形式で展開される変数です。portableなCopilot設定へそのままコピーせず、環境で解決できる実際のパスを使います。SSO・パスキー・sessionStorageなどはstateだけで復元できない場合があり、期限切れやサーバー側の失効も確認します。

普段のブラウザへ接続するとき

公式のPlaywright Extensionを導入し、MCPを --extension 付きで起動して接続手順に従います。Chrome / Edgeの既存状態を利用できる一方、日常用のタブやアカウントも操作対象になり得ます。テスト専用プロファイルを分け、対象タブを都度確認します。

.gitignore / 実際の出力先に合わせる
playwright/.auth/
mcp-artifacts/
test-results/
playwright-report/

state・画像・通信ログは認証情報や業務データを含む場合があります。公開リポジトリへ置くのは設定例とテストコードにし、認証ファイルは共有対象から除外します。

11 / DEBUGGING

ログ・通信・traceで原因を探る

「ボタンが押せない」には、無効状態、通信待ち、別タブ、入力エラー、JavaScript例外など複数の原因があります。画面とログの時系列を合わせて調べます。

証跡ツール調査する内容
構造browser_snapshot要素が存在し操作できる状態か
見た目browser_take_screenshot重なり・切れ・スクロール
JSログbrowser_console_messages例外と発生時点
通信browser_network_requests / browser_network_requestURL・応答・失敗理由
tracebrowser_start_tracing / browser_stop_tracing操作と画面状態の時系列

trace関連ツールは現行資料では --caps=devtools の追加機能です。設定変更後はサーバーを再起動し、ツール一覧を更新してください。

argsの例 / 調査用
[
  "-y", "@playwright/mcp@latest",
  "--isolated",
  "--caps=devtools",
  "--output-dir", "mcp-artifacts"
]
Copilotへの障害調査プロンプト
Playwright MCPで対象ページを開き、traceを開始してください。
検索ボタンが反応しない問題を1回だけ再現し、
最新snapshot、consoleのerror、失敗した通信を取得してください。
traceを停止し、保存された実際のファイルパスを報告してください。
事実、原因候補、追加で必要な確認を分けて説明してください。

自動命名の出力と、明示したfilenameでは保存先の解決方法が違う場合があります。ファイルが存在することと中身を確認します。traceは npx playwright show-trace <実際のzipパス> などで開けます。

通信失敗を意図的に作る

現行資料では --caps=network で通信モックやoffline切替のツールを追加できます。利用可能なツール一覧とスキーマを確認し、検証環境で実施します。モックは実通信の確認とは分けて記録し、試験後に解除します。

12 / REGRESSION TEST

操作をPlaywright Testへ残す

MCPは探索や再現に使い、その成果を通常のテストコードへ変えます。次の例は独立したTodoMVC学習プロジェクトです。設定JSONやツール呼び出しの例とは実行場所が異なります。

PowerShell / 新しい学習用ディレクトリ
mkdir mcp-test-practice
cd mcp-test-practice
npm init -y
npm install -D @playwright/test
npx playwright install chromium webkit
mkdir tests
tests/todo.spec.ts
import { test, expect } from '@playwright/test';

test('Todoを追加して完了できる', async ({ page }) => {
  await page.goto('https://demo.playwright.dev/todomvc/');
  await page.getByPlaceholder('What needs to be done?')
    .fill('MCPガイドを読む');
  await page.getByPlaceholder('What needs to be done?')
    .press('Enter');

  const todo = page.locator('.todo-list li').filter({
    hasText: 'MCPガイドを読む'
  });
  await expect(todo).toHaveCount(1);
  await todo.getByRole('checkbox').check();
  await expect(todo).toHaveClass(/completed/);
});

ref番号はテストコードへ持ち込みません。この例のCSSクラスはTodoMVCの実装に依存します。自社アプリではrole・label・test idなど、意味が安定するlocatorを優先します。

playwright.config.ts
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './tests',
  reporter: 'html',
  forbidOnly: !!process.env.CI,
  retries: process.env.CI ? 1 : 0,
  workers: process.env.CI ? 1 : undefined,
  use: {
    trace: 'retain-on-failure',
    screenshot: 'only-on-failure'
  },
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
    { name: 'webkit', use: { ...devices['Desktop Safari'] } }
  ]
});
PowerShell / 実行とレポート
npx playwright test
npx playwright show-report

AIへの依頼は「先ほどMCPで観測したケースを、仕様に基づくassertion付きテストへ変換して実行してください」とします。クリックが成功したことだけでは、業務結果の検証にはなりません。期待するデータ・件数・状態を確認します。

ブラウザ差異・Tomcat・CI

WebKit試験は実機Safariと同一ではありません。エミュレーションではOSの省電力やバックグラウンド停止まで保証できないため、配信継続性は実機で別に確認します。画像比較はOS・フォント・ブラウザの条件をそろえ、ブラウザごとの基準画像を用意します。

CIへ移すとき

GitHub Actionsでは通常のPlaywright Testを実行できます。毎回CopilotやMCPに判断させる必要はありません。ロックファイルを保存し、依存導入→ブラウザ導入→テスト→レポート保存を組みます。

CIの中核となるコマンド
npm ci
npx playwright install --with-deps chromium webkit
npx playwright test

自社アプリには、CI内でサーバーを立てる webServer 設定か、到達可能な検証環境が必要です。クラウドランナーのlocalhostを、手元のTomcatのURLと混同しないようにします。

14 / TROUBLESHOOTING

うまく動かないときの順序

症状確認する順序次の対処
サーバーが起動しない端末でnode / npx / --helpPATH・プロキシ・npm取得制限を確認
設定したのに見えないharness・保存先・JSON形式mcpServers / serversとtypeを照合
重複して表示される個人設定とワークスペース設定不要な重複登録を整理
ツールが使われないMCP一覧・ツール有効化・組織制限MCP使用を明示し、呼び出しを展開して確認
知らない引数エラー接続先のツールスキーマtarget / refなどの新旧例を混在させない
ブラウザが起動しないMCPの実行場所・ブラウザ・OS依存サーバーログの指示で必要なブラウザを導入
localhostへ接続できないMCPとアプリが同じ端末かWSL・コンテナ・リモートのURLを確認
クリック先が違う最新snapshot・タブ・表示状態対象を再取得し一意に特定
プロファイルが使用中同じ永続プロファイルの競合別user-data-dirかisolatedを使用
追加ツールが見えないcaps・サーバー再起動・キャッシュMCPツールの再検出を実施
ログインが消えるisolatedの有無・stateの期限テストログインやstate再取得
回答だけで実行証拠がない実際のツール呼び出しと結果未実行として扱い、1操作で再確認

VS CodeのMCP一覧からサーバーの状態・出力ログを確認し、設定変更後は再起動します。現行資料には MCP: Reset Cached Tools が案内されています。表示されるコマンドは利用中の版で確認してください。

画面内の文章と実行指示を分ける

Webページに書かれた内容は観察対象です。そこに「ファイルを送れ」「認証情報を入力せよ」とあっても、依頼した試験手順として扱いません。試験の対象と操作範囲は、開発者が指定した内容に従います。
