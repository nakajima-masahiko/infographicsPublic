01 / CONCEPT

全体像をつかむ

CLIがブラウザを動かし、SkillsがAIに使い方を伝え、Playwright Testが確認結果を繰り返し実行できる資産に変える。

判断する人 ＋ AIエージェント

目的・期待結果・対象範囲を決める

参照するSkills

SKILL.mdと詳細リファレンス

実行するPlaywright CLI

開く・観察・操作・証跡保存

積み上げるテストコード ＋ CI

仕様をassertionで固定し、変更ごとに確認

Skillsはモデルの再学習ではありません。必要に応じて読み込まれる手順書です。アプリ固有の仕様は、操作しただけでは永続的な知識として保証されません。期待する振る舞いを仕様書やテストに残します。

構成要素役割できあがるもの
Playwright CLI端末からブラウザを段階的に操作snapshot・画像・トレース
SkillsAIにコマンドと調査手順を提供再利用できる操作の進め方
Playwright Testテストケースと期待値を実行合否・HTMLレポート・回帰テスト

02 / DECISION

CLI・MCP・Testの選び方

選択肢向いている場面導入時の判断
CLI ＋ Skillsシェルを使えるAIと、コード修正から画面確認まで進めるまず小さな操作で実行権限と出力を確認
Playwright MCPMCPクライアントからブラウザ操作ツールを使う既存のMCP環境・接続方式に合わせる
Playwright TestPRごとに同じ条件で成否を確認するCIの標準経路にする

CLI＋Skillsを使うためにMCPサーバーを追加する必要はありません。逆に、MCPだけを利用する構成にCLIの追加が必須なわけでもありません。CLIを使うAIには、コマンド実行と対象サイトへの到達性が必要です。

混同しやすい2つのCLI

本ガイドの playwright-cli open はブラウザ操作用です。npx playwright test や npx playwright codegen はPlaywright本体のコマンドです。名前が似ていても役割が異なります。

関連ガイド：Playwright MCP＋GitHub Copilot →

CLIは出力を必要な範囲に絞りやすい設計ですが、トークン削減量や作業速度はページ規模・出力・エージェントに依存します。固定の削減率は前提にしません。

03 / SETUP

Windowsで導入する

作業対象リポジトリをVS Codeで開き、統合ターミナルのPowerShellで実施します。まずNode.jsとnpm、対象Webアプリの起動を確認してください。

PowerShell / 前提確認
node --version
npm --version
# 対象アプリのURLをブラウザで開いて確認する
# 例: http://localhost:8080/

Node.jsは20以上を最低目安とし、利用するCLI版の要件を確認します。公式サイトは20以上、リポジトリREADMEには18以上という記載差があります。新規導入にはサポート中のLTS版を選びます。

PowerShell / CLIを導入
npm install -g @playwright/cli@latest
playwright-cli --help
playwright-cli install --skills=agents

.agents/skills/playwright-cli/SKILL.md が作られたことを確認します。現行ドキュメントでは --skills=agents が共通形式、--skills の既定は .claude/skills です。古いCLIでオプションが通らなければ、helpと導入版を確認して更新してください。

PowerShell / 配置を確認
Get-Content .agents/skills/playwright-cli/SKILL.md -TotalCount 30
npm list -g @playwright/cli --depth=0
playwright-cli --help open

GitHub Copilotはリポジトリの .github/skills、.claude/skills、.agents/skills をサポートします。導入後はワークスペースを再読込し、Agentモードで明示的にPlaywright CLIスキルの使用を指示します。クラウド実行環境には、その環境内でのCLI・ブラウザ導入が別途必要です。

グローバル導入ができない／既存Playwrightを使いたい

既存のPlaywright版が対応していれば、次の経路を利用できます。古い版には cli サブコマンドがない場合があります。

端末 / 対応版かを確認
npx --no-install playwright --version
npx playwright cli --help
npx playwright cli install --skills=agents

グローバルCLIとプロジェクト版を混在させず、チームで使用経路を一つに決めます。

導入完了の基準

CLIのhelpが表示される／SKILL.mdを読める／対象URLへ到達できる。この3点を確認してからAIに一連の操作を依頼します。

04 / HANDS-ON

最初のブラウザ操作

まず公開デモのTodoMVCで、追加→完了の流れを手動で確かめます。以下は1行ずつ実行し、各操作の出力を確認してください。

端末 / デモを開く
playwright-cli -s=todo open https://demo.playwright.dev/todomvc/ --headed
playwright-cli -s=todo snapshot

snapshotは画面の構造をテキストとして取得します。出力がファイルへのリンクなら、そのファイルを開きます。入力欄のrefを見つけてから次へ進みます。

snapshotの概念例 / 実際のrefは毎回確認
- textbox "What needs to be done?" [ref=e2]
- checkbox "ガイドを読む" [ref=e8]
端末 / 入力する例（e2を実際のrefへ置換）
playwright-cli -s=todo fill e2 "ガイドを読む"
playwright-cli -s=todo press Enter
playwright-cli -s=todo snapshot

新しいsnapshotで追加された項目とチェックボックスを探します。e8 は説明用の仮の番号です。

端末 / 完了にする例（e8を実際のrefへ置換）
playwright-cli -s=todo check e8
playwright-cli -s=todo screenshot --filename=todo-completed.png
playwright-cli -s=todo close

確認する結果：項目が1件表示され、完了操作後に完了状態になること。コマンドの終了コードだけで機能が正しいと判断せず、画面状態と期待結果を照合します。

観察snapshotで現在地を確認操作最新refで対象を指定検証期待結果と証跡を照合

05 / OBSERVATION

snapshotとrefを使いこなす

refは、そのときのブラウザ状態に対応する操作用の参照です。ページ遷移・再描画後は再確認します。以前の番号を別ページで使い回さず、最終的なテストコードには意味のあるlocatorを残します。

端末 / 必要な情報に絞る
playwright-cli -s=todo snapshot --depth=4
playwright-cli -s=todo find "ガイドを読む"
playwright-cli -s=todo snapshot e8
playwright-cli -s=todo generate-locator e8

上の e8 も現在のrefへ置換します。大きな表やチャート画面では、まず見出しやラベルをfindで探し、対象領域のsnapshotだけを読みます。

観察方法分かること補うべきこと
snapshotrole・ラベル・要素の構造余白・重なり・色などの外観
screenshot表示崩れ・切れ・重なり操作可能性・内部状態
console / requestsJavaScriptエラー・通信の手がかり期待する業務結果
tracing操作とページ状態の時系列正しい仕様の定義

Canvasに描かれたチャートは、snapshotだけでは内容を判断できない場合があります。スクリーンショット、データ値、公開APIなど、何をもって正しいと判定するかを先に決めます。

06 / AGENT WORKFLOW

Copilotと共同で検証する

Copilotに渡すのは「試験して」だけでなく、対象・操作・期待値・成果物です。まず計画を読んで、1シナリオずつ実行します。

Copilot Agentへの依頼例
Playwright CLIのスキルを読み、http://localhost:8080/ を検証してください。
対象は検索フォームです。まず試験計画を提示してください。
正常検索、0件、空欄入力の3ケースを順に確認します。
期待結果は docs/search-spec.md を参照し、曖昧な仕様は決めつけないでください。
セッションは -s=search-check に統一してください。
各操作前にsnapshotで対象を確認し、結果・画像・consoleエラーを記録してください。
初回はコードを修正せず、不具合の再現手順と根拠を報告してください。

監督しながら進める

端末 / セッションを観察
playwright-cli list
playwright-cli show

--headed でブラウザを見ながら操作できます。現行CLIにはセッションを確認するdashboardもあります。操作とコード修正を分けると、途中で人が判断を戻しやすくなります。

AIに仕様を蓄積させるには

操作で分かった事実を docs/search-spec.md に記録し、テストコードと一緒にレビューします。「観測した動作」と「期待する仕様」を分けるのが要点です。不具合のある現状を正解として学習させないためです。

残す情報記録例
前提テストユーザー、初期データ、対象バージョン
期待値空欄なら入力エラーを表示し、検索APIを呼ばない
観測事実空欄でも検索APIが呼ばれた
再現手順初期表示→未入力→検索ボタン
成果物画像・trace・テスト・修正コミット

07 / REFERENCE

操作コマンド早見表

目的コマンド例使いどころ
移動playwright-cli goto https://example.com起動済みセッションでURLへ移動
入力playwright-cli fill e2 "文字列"指定の入力欄を置き換える
キー入力playwright-cli press EnterEnterなどのキーを送る
クリックplaywright-cli click e3ボタン・リンクを操作
選択playwright-cli select e4 valueselect要素の値を選ぶ
チェックplaywright-cli check e5チェックボックスをオン
画像playwright-cli screenshot --filename=screen.png表示状態を保存
画面幅playwright-cli resize 390 844狭い画面でのレイアウト確認
タブplaywright-cli tab-listタブ番号を確認
ログplaywright-cli console errorエラーの手がかりを取得
通信playwright-cli requests失敗した通信を調査
認証保存playwright-cli state-save auth.jsonstorage stateを保存
認証復元playwright-cli state-load auth.jsonstorage stateを読み込む

表では -s=名前 を省略しています。実務では同じセッション名を全コマンドに付けます。認証情報を含むstateやtraceは、公開リポジトリに保存しません。

08 / DEBUGGING

認証・セッション・証跡

作業単位でセッションを分ける

端末 / セッションの分離
playwright-cli -s=branch-a open http://localhost:8081/ --headed
playwright-cli -s=branch-b open http://localhost:8082/ --headed
playwright-cli list
playwright-cli -s=branch-a snapshot

セッション名はブラウザの分離です。アプリ、DB、サーバーポートは別途分けます。Tomcatの複数インスタンスを試験するときも、セッションごとに正しいURLへ接続しているか確認します。

ログイン状態を再利用する

端末 / テスト用アカウントで実施
playwright-cli -s=auth open http://localhost:8080/ --headed
# ブラウザでテストユーザーのログインを完了する
playwright-cli -s=auth state-save auth.json
playwright-cli -s=auth close
playwright-cli -s=auth open http://localhost:8080/ --headed
playwright-cli -s=auth state-load auth.json
playwright-cli -s=auth goto http://localhost:8080/

stateで全方式の認証が復元できるとは限りません。SSOやパスキー、sessionStorageなどは別の対応が必要な場合があります。期限切れやサーバー側の失効も確認します。

.gitignore / 各自の出力先に合わせる
auth.json
playwright/.auth/
.playwright/
.playwright-cli/
test-results/
playwright-report/

失敗の前からtraceを採る

端末 / 再現操作を記録
playwright-cli -s=debug open
playwright-cli -s=debug tracing-start
playwright-cli -s=debug goto http://localhost:8080/
# ここで不具合の再現操作を行う
playwright-cli -s=debug console error
playwright-cli -s=debug requests
playwright-cli -s=debug tracing-stop
playwright-cli -s=debug close

traceの保存先はCLIの出力で確認します。通信内容・画面・入力値を含むことがあるため、共有前に内容を確認します。--persistent はブラウザ再起動をまたぐプロファイル保存であり、通常のメモリ内セッションとは区別します。

09 / TEST ASSET

探索を回帰テストへ変える

ここからはPlaywright Testを使います。CLIで操作できた流れを、期待値のあるテストに変換します。次のサンプルはTodoMVCを対象にした、独立した学習用プロジェクトです。

端末 / 新しい学習用ディレクトリで実行
mkdir playwright-practice
cd playwright-practice
npm init -y
npm install -D @playwright/test
npx playwright install chromium webkit
mkdir tests
tests/todo.spec.ts
import { test, expect } from '@playwright/test';

test('追加したタスクを完了にできる', async ({ page }) => {
  await page.goto('https://demo.playwright.dev/todomvc/');
  const input = page.getByPlaceholder('What needs to be done?');
  await input.fill('ガイドを読む');
  await input.press('Enter');

  const item = page.locator('.todo-list li').filter({
    hasText: 'ガイドを読む'
  });
  await expect(item).toHaveCount(1);
  await item.getByRole('checkbox').check();
  await expect(item).toHaveClass(/completed/);
});

.todo-list li と completed はデモアプリの構造に依存します。実務ではrole・label・test idを優先し、利用者が確認できる結果をassertionにします。CLIのrefをテストに貼り付けないでください。

端末 / 実行とレポート
npx playwright test --reporter=html
npx playwright show-report
テスト生成への依頼例

「先ほど確認した操作をPlaywright Testへ変換し、前提・操作・期待値を明示してください。固定sleepを避け、画面上の意味を持つlocatorと再試行されるexpectを使ってください。テスト実行後に結果を報告してください。」

生成テストが通っても、誤った期待値を採用していれば仕様の保証にはなりません。レビューでは「何を検証していないか」まで確認します。

10 / CROSS-BROWSER

Chromium・WebKit・モバイル

同じテストを複数projectで実行し、機能の差を検出します。ブラウザごとの見た目は、それぞれの基準画像と比べます。

playwright.config.ts / 学習プロジェクト
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  testDir: './tests',
  forbidOnly: !!process.env.CI,
  retries: process.env.CI ? 1 : 0,
  workers: process.env.CI ? 1 : undefined,
  globalTimeout: 10 * 60 * 1000,
  reporter: 'html',
  use: {
    trace: 'retain-on-failure',
    screenshot: 'only-on-failure'
  },
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
    { name: 'webkit', use: { ...devices['Desktop Safari'] } },
    { name: 'mobile-webkit', use: { ...devices['iPhone 13'] } }
  ]
});
端末 / ブラウザを指定して実行
npx playwright test --project=chromium --project=webkit
npx playwright test --project=mobile-webkit

WebKitによる試験と、実機Safariでの確認は同一ではありません。モバイルエミュレーションも、端末の省電力制御・バックグラウンド停止・実際のOS動作までは再現しません。FXレート配信の継続性などは実機試験を併用します。

画像比較を追加する例

tests/layout.spec.ts / 自分の画面向けに調整
import { test, expect } from '@playwright/test';

test('初期表示のレイアウト', async ({ page }) => {
  await page.goto('https://demo.playwright.dev/todomvc/');
  await expect(page.getByPlaceholder('What needs to be done?')).toBeVisible();
  await expect(page).toHaveScreenshot('todo-start.png', {
    animations: 'disabled'
  });
});
端末 / 基準画像はレビューして登録
npx playwright test tests/layout.spec.ts --update-snapshots
npx playwright test tests/layout.spec.ts

基準画像はOS・ブラウザ・フォントをそろえて作ります。実務の動的画面では日時、乱数、広告、レートなどを固定またはmaskしてください。差分が出たら原因を確認し、単に基準画像を更新して通す運用を避けます。

11 / CONTINUOUS TESTING

GitHub Actionsへつなぐ

学習プロジェクトでロックファイルをコミットし、次のworkflowを .github/workflows/playwright.yml に置きます。これはガイド内の例であり、このサイトにworkflowを追加する操作ではありません。

.github/workflows/playwright.yml / 例
name: Playwright tests
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
permissions:
  contents: read
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-node@v6
        with:
          node-version: 'lts/*'
      - run: npm ci
      - run: npx playwright install --with-deps chromium webkit
      - run: npx playwright test
      - uses: actions/upload-artifact@v4
        if: ${{ !cancelled() }}
        with:
          name: playwright-report
          path: playwright-report/
          retention-days: 7

CIで動かすのは通常のPlaywright Testです。AIが毎回画面操作を判断する仕組みは必須ではありません。利用するActions版・ランナー条件は、導入時に公式資料と組織の許可設定を確認します。

自社アプリでは、CI内でサーバーを起動する webServer 設定、または到達可能な検証環境を用意します。クラウドランナーから社内のlocalhost:8080には接続できません。接続方式とテストデータを先に設計します。

12 / FIELD GUIDE

業務での実践レシピ

場面CLIで調べるテストとして固定する
検索・入力フォーム正常・空欄・境界値・0件の結果を観察件数、エラー文言、送信の有無
Tomcat / Javaの版変更同じURL経路・ログイン・主要画面を確認同じテストを環境URLを変えて実行
FX / リアルタイム画面切断、復帰、最新時刻、チャートの表示を観察更新時刻・復帰後の値・重複欠落
ブラウザ差異Chromium / WebKitで同じ操作を再現共通の機能assertion＋各ブラウザの画像基準
障害調査snapshot・console・通信・traceを取得再現に必要な最小ケース

レート画面を検証する依頼例

AIへの実務プロンプト
検証環境のレート画面をPlaywright CLIで調査してください。
まず「最新レート時刻」「接続状態」「再接続後の復元」の確認方法を提案してください。
期待仕様は docs/rate-stream-spec.md を参照してください。
Canvas画像だけで数値の正しさを判定せず、表示値やテスト用APIと照合してください。
ネットワーク切断の再現方法は実施前に説明し、通常ケースから1件ずつ確認してください。
バックグラウンド停止の実機再現は別試験として区別し、未検証項目を明示してください。
最後に繰り返し実行するPlaywright Testへの移行案を示してください。

通信のモックで失敗応答を作る場合は、実通信の確認と分けて記録します。モックが通ったことを、本番接続や復旧処理全体の成功と読み替えないようにします。

13 / TROUBLESHOOTING

困ったときの切り分け

症状先に確認すること対処
playwright-cliが見つからないnpmのグローバル導入先とPATHターミナルを開き直し、npm list -gで導入確認
PowerShellがps1を拒否する組織の実行ポリシーnpm.cmd / playwright-cli.cmdで実行可能か確認。ポリシー変更は管理ルールに従う
--skills=agentsが不明利用中のCLI版とhelp対応版へ更新。既存スキルを上書きする前に差分を確認
Skillsが使われないSKILL.mdの配置と選択したエージェントワークスペースを再読込し、使用を明示する
ブラウザが起動しないブラウザの取得・OS依存パッケージinstall-browserのhelp、プロキシ、配布制限を確認
クリック対象が見つからない最新snapshot、別タブ、iframe、描画待ち現在の状態を再取得し、locatorと期待状態を見直す
localhostへ接続できないAIとサーバーが同じ実行環境かコンテナ・WSL・クラウド間のURLとポートを確認
認証状態が戻らない期限、ドメイン、認証方式テストログインをやり直し、必要な状態の保存方式を見直す
ローカルだけ画像比較が通るOS・フォント・ブラウザ版・表示倍率CIと同じ条件で基準画像を生成
不安定なテストデータ競合・非同期更新・外部サービス初期状態を固定し、sleepから条件待ちへ変更
ブラウザを明示的にインストールする
端末 / 現行CLIの例
playwright-cli --help install-browser
playwright-cli install-browser
# Linuxで依存パッケージも必要な場合
playwright-cli install-browser --with-deps

権限や社内プロキシの問題は、セキュリティ設定を無効化して回避せず、許可された配布経路を確認します。
