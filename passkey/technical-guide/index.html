01 / FOUNDATIONS

パスキーとは何か

サービスごとのパスワードに代わり、暗号鍵で「そのアカウントの認証手段を使えること」を証明する仕組みです。

利用者は端末の顔認証・指紋認証・PINなどで操作を承認します。サービスは公開鍵で検証します。生体認証は端末側の本人確認方法の一つであり、パスキーそのものではありません。

観点パスワードパスキー
認証の根拠秘密の文字列を知っている対応する秘密鍵による署名を検証できる
サービス側の保存通常はパスワードのハッシュ等Credential IDと公開鍵等
利用者の操作入力・パスワード管理ツールの利用端末の案内に従い本人確認
偽サイトへの耐性入力内容を渡してしまう可能性RP ID・Originに結びついた認証
導入後も必要復旧・不正対策・セッション管理復旧・不正対策・セッション管理
先に押さえる3点

① 鍵はサービスごとに作る。② 生体情報をサービスへ送らない。③ ログインの強化と、身元確認・権限管理は別に設計する。

このガイドの読み方

仕組みを知る02〜08章 / 登録・認証・データ実装を設計する09〜13章 / Web・既存基盤・運用本番へ進める14〜17章 / 試験・展開・チェック

対象はWeb開発者・設計者・認証基盤担当者です。HTTP、Cookie、API、公開鍵暗号の基礎を前提に、必要な用語はその場で説明します。

参照：[1] / [2]

02 / ARCHITECTURE

4つの役割を分けて理解する

役割担当すること担当しないこと
RP（Relying Party）サービス。challenge発行、公開鍵保存、検証、セッション発行端末の顔画像や指紋を照合すること
クライアントブラウザ・OS。Originを扱い、WebAuthn要求を認証器へ仲介サーバーに代わって最終的な認証成功を決めること
認証器（Authenticator）鍵の生成・保持、利用者確認、署名利用者の業務権限を決めること
パスキープロバイダーパスキーの保存・同期・利用を支援する仕組みRPの顧客アカウント管理をすべて肩代わりすること
サービスの信頼境界

RP / 認証サーバー

Credential ID・公開鍵・アカウントの対応
検証結果からセッションを作成

HTTPSで要求と応答を交換
利用者側の境界

ブラウザ・OS → 認証器

サイトを確認し、端末側で操作を承認
署名を返す。秘密鍵はRPへ渡さない

WebAuthnとCTAPの違い

FIDO2はWebAuthnとCTAPを組み合わせた標準体系です。パスキーは、その公開鍵資格情報をパスワードに代わる認証に使う考え方・利用体験として理解できます。FIDO2対応という表示だけで、同期・UV・discoverable credentialのすべてを保証するわけではありません。

WebAuthnはWebアプリが認証器を使うためのAPIと認証手順です。CTAPはクライアントと外付け認証器などの間の通信を定めます。WebアプリがUSBやBluetoothを直接制御して署名させる構成ではありません。

秘密鍵が同期される場合、その保護・復元にはプロバイダーの設計も関わります。「秘密鍵はRPに送らない」と「秘密鍵は一台の端末から絶対に出ない」は異なります。

参照：[1] / [2]

03 / CREDENTIAL MODELS

同期型・端末固定型・端末間利用

方式特徴設計上の確認
同期型パスキープロバイダーを介し複数端末で利用できる同期アカウントの保護・復旧、組織ポリシー
端末固定型パスキー特定の認証器に結びつき、同期されない紛失時の予備認証器、配布・回収・廃棄
別端末を使う認証PCからスマートフォン等のパスキーを利用する経路QRコード・近接確認・端末条件を実機確認

「同期」と「別端末での認証」は別の仕組みです。PCに表示された案内からスマートフォンを使う場合でも、必ずしも秘密鍵をPCへコピーしているわけではありません。QRコードが常に出るとも限りません。

Discoverable credentialとは

RPが事前にCredential IDを列挙しなくても、認証器側でアカウント候補を見つけられる資格情報です。ユーザー名入力なしの体験やAutofillに関わります。residentKeyの設定は保存・発見の性質、userVerificationは本人確認の要求です。混同しないでください。

セキュリティキーなら、すべて同じではない

セキュリティキーの機種・設定・対応プロトコルによって、discoverable credentialやPIN、UVへの対応は異なります。製品形状だけで要件を満たすと判断しません。

参照：[1] / [2] / [5]

04 / THREAT MODEL

防げる攻撃と、残るリスク

脅威パスキーによる改善別途必要な対策
フィッシング別のRP IDの鍵は偽サイトで利用できないドメイン管理、残存認証・復旧経路の強化
パスワード使い回しパスキー経路には使い回す文字列がないパスワード併用経路への防御
認証応答の再送使い捨てchallengeで再利用を拒否できるサーバーで有効期限・単回使用を強制
サーバーDB漏えい公開鍵から通常は秘密鍵を復元できない個人情報・DB・管理権限の保護
端末・セッション侵害認証方式だけでは完全に解決しない端末対策、XSS対策、セッション失効、再認証
不正なパスキー追加既存セッションが弱いと攻撃者の鍵を登録される登録前の再認証・通知・監査

UPとUVは同じではない

UP（User Presence）は利用者が操作に関与したこと、UV（User Verification）は認証器がPINや生体認証等で利用者を確認したことを示します。タッチだけでUVを満たすとは限りません。

このガイドの設計例は、登録・認証にUVを必須とします。クライアントへのuserVerification: 'required'の指定だけでなく、サーバー検証でもUVを要求します。対応しない環境向けの別経路は明示的に設計します。

「顔認証だから多要素」とだけ説明しない

パスキーの所持とローカルの本人確認は複数要素の性質を持ち得ますが、規制や社内基準への適合は、同期型の扱い・認証器の保証・復旧まで含めて判断します。

参照：[1] / [2] / [7]

05 / RP ID & ORIGIN

RP IDとOriginを、最初に決める

項目例意味
Originhttps://login.example.comスキーム＋ホスト＋ポート。サーバーは信頼する値と照合
RP IDexample.com鍵が紐づくドメイン。スキーム・ポート・パスを含めない
許容Originの設定https://login.example.com を明示リクエストのHost等を無条件に信用して生成しない
開発環境localhostlocalhostの例外を使える場合がある。本番はHTTPS
複数サービスlogin / shop / app 等共通RP IDの利点と、サブドメインの信頼境界を評価

通常、RP IDには呼び出し元ホスト自身か、その登録可能ドメインのサフィックスを指定します。公開サフィックスは指定できません。例えばlogin.example.comからexample.comを選ぶ構成は可能ですが、任意の別ドメインは選べません。

RP IDを広げると、複数サブドメインで同じ資格情報を利用する設計が可能になります。その分、各サブドメインと許容Originを誰が管理するかが重要です。侵害された正規Originでの攻撃まで、パスキーが無条件に防ぐわけではありません。

後からの変更は「URLを書き換える」だけでは済まない

鍵は作成時のRP IDに結びつきます。ドメイン移転・ブランド統合・テナント分割の予定を先に確認してください。Related Origin Requestsのような拡張は対応状況と追加要件を確認し、初期導入の前提にしない設計も検討します。

参照：[1] / [6] / [7]

06 / REGISTRATION

登録：公開鍵をアカウントに結びつける

登録は「端末で鍵を作る」だけで完了しません。誰のアカウントに、誰がその鍵を追加できるかを最初に確定します。

  1. 登録の権限を確認

    既存利用者は十分に新しい再認証を要求。新規利用者はアカウント作成・身元確認の方針を別途適用します。

  2. サーバーが登録オプションを発行

    ランダムなchallenge、RP、user handle、アルゴリズム、UV条件、既存Credential IDの除外候補を返します。

  3. ブラウザが認証器へ作成を依頼

    navigator.credentials.create()を仲介し、利用者が保存先と本人確認を承認します。

  4. 応答をサーバーで検証

    challenge・Origin・RP ID・フラグ・公開鍵等をライブラリで検証し、対象アカウントとの紐付けを確定します。

  5. DB保存・通知

    Credential IDの重複を拒否し、公開鍵などを保存。利用者に新しいパスキーが追加されたことを知らせます。

主なオプションこのガイドでの考え方
user.id推測しにくい安定したバイト列（最大64バイト）。メールアドレスや表示名とは分ける
excludeCredentials登録済みCredential IDを渡し、同じ資格情報の重複作成を避ける
residentKeyユーザー名なし認証を目的に、requiredを例示
userVerificationrequired。サーバー側も対応する条件を検証
attestation一般向けではnoneを基本に検討。認証器の来歴を保証したい場合は別途ポリシー化

参照：[1] / [3] / [6]

07 / AUTHENTICATION

認証：署名を検証して、セッションを発行する

毎回異なるchallengeに対する署名で認証します。ネットワークでパスワード相当の固定文字列を送り続ける方式ではありません。

サーバーで確認すること

  • clientDataJSON.typeが認証用で、challengeが発行済み取引と一致する。
  • Originが許容値と一致し、認証器データのRP IDハッシュが期待値と一致する。
  • 必要なUP・UVが満たされ、保存済み公開鍵で署名を検証できる。
  • Credential IDが有効で、アカウントが停止・削除されていない。
  • discoverable認証ではuser handleとCredential IDから同じアカウントに解決できる。
  • challengeを単回で消費し、認証完了後にセッションIDを更新する。

何に署名するのか

概念的にはauthenticatorData || SHA-256(clientDataJSON)に署名します。authenticatorDataにはRP IDのハッシュやフラグなどが含まれ、クライアントデータにはchallengeやOriginなどが含まれます。JSONを独自に作り直すと検証対象が変わるため、元のバイト列と対応ライブラリを使います。

challengeをブラウザ任せにしない

サーバーで暗号学的乱数から生成し、短い有効期限・操作種別・セッションや取引との関連を記録します。複数タブは取引IDごとに管理し、並行送信でも一度しか成功しないようにします。

参照：[1] / [7]

08 / DATA MODEL

公開鍵と資格情報の保存設計

データ保存・利用の目的注意点
user handle認証用の不変な利用者IDユーザー名変更でも維持。個人情報を直接入れない
Credential ID資格情報の検索・一意制約Base64URL文字列等で一貫して保存
credential public key署名検証COSE形式等のバイト列を壊さず保存。ライブラリの型に戻す
signCount署名カウンターの比較常に0の認証器もある。同期型を踏まえて判定
transports認証器への到達候補のヒント認証保証や端末所有の証明として使わない
BE / BSバックアップ可能性・現在の状態端末名や本人の身元を証明する値ではない
AAGUID / attestation認証器の種類や来歴評価の材料AAGUIDだけで認証器を信頼しない。利用者個体IDではない
表示名・登録日時・最終利用・失効日時資格情報の管理画面と監査利用者が名前を変更できる。認証を依存させない

アカウントとパスキーを1対多にする

一人の利用者がスマートフォン用・セキュリティキー用など複数の資格情報を持てるようにします。資格情報の失効はアカウント全体の削除と分け、失効したCredential IDは検証前に拒否します。

カウンターは「増えない＝必ず不正」ではない

ゼロ固定の認証器や並行処理も考慮します。非ゼロの保存値に対して増分が不自然なら調査材料になりますが、現在の要求が複製側か正規側かを一意に判定できるわけではありません。ライブラリの挙動と業務リスクを確認します。

秘密鍵・端末のPIN・生体データはRPのDBに保存しません。一方、公開鍵だけのDBであってもアカウント紐付けの改ざんは重大なため、更新権限・監査・バックアップを保護します。

参照：[1] / [3] / [9]

09 / CLIENT IMPLEMENTATION

ブラウザ実装：開始・応答・結果表示

以下は@simplewebauthn/browserを使う、独自の説明用コードです。対応する4つのAPI、CSRFトークン、UI要素はアプリ側で実装します。この技術ガイド自体はパスキーを作成しません。

端末 / 学習プロジェクトで導入
npm install @simplewebauthn/browser@14 @simplewebauthn/server@14
# 正確なパッチ版はpackage-lock.jsonで固定し、更新時に再検証する
client.js / ボタンから明示的に開始する例
import { startRegistration, startAuthentication }
  from '@simplewebauthn/browser';

async function postJSON(url, body) {
  const csrf = document.querySelector('meta[name="csrf-token"]').content;
  const response = await fetch(url, {
    method: 'POST', credentials: 'same-origin',
    headers: { 'Content-Type': 'application/json', 'X-CSRF-Token': csrf },
    body: JSON.stringify(body),
  });
  if (!response.ok) throw new Error('API_REQUEST_FAILED');
  return response.json();
}

// UI側で二重起動を抑え、try/catch/finallyで状態を復元する。
export async function registerPasskey() {
  const { transactionId, options } =
    await postJSON('/api/passkeys/register/options', {});
  const response = await startRegistration({ optionsJSON: options });
  const result = await postJSON('/api/passkeys/register/verify', {
    transactionId, response,
  });
  if (!result.verified) throw new Error('REGISTRATION_REJECTED');
  return result; // サーバー側の保存完了を確認して成功表示
}

export async function signInWithPasskey() {
  const { transactionId, options } =
    await postJSON('/api/passkeys/auth/options', {});
  const response = await startAuthentication({ optionsJSON: options });
  const result = await postJSON('/api/passkeys/auth/verify', {
    transactionId, response,
  });
  if (!result.verified) throw new Error('AUTHENTICATION_REJECTED');
  return result; // 検証成功後のセッションはサーバーが発行
}

実装時に補うこと

  • ビルド環境でES Modulesをbundleし、依存版を固定します。上記は単体HTMLに貼るだけでは動きません。
  • 機能検出を行い、非対応時は案内を表示します。利用者がキャンセルしたら再試行できる状態へ戻します。
  • ブラウザの成功応答だけでログイン済みと扱わず、サーバー検証の結果を待ちます。
  • ネイティブWebAuthn APIを直接使う場合、challenge・user.id・Credential ID等のバイト列とBase64URLの変換を正しく処理します。

参照：[4]

10 / SERVER IMPLEMENTATION

サーバー実装：検証を中心に組み立てる

以下はSimpleWebAuthn 14系のAPI形状を使う設計例です。txStore、db、sessionsは説明用の抽象インターフェースであり、そのまま起動できるサーバーではありません。導入時点の対応Node.js版・型定義・エラー仕様も確認してください。

server.js / 登録オプション生成の設計例
import {
  generateRegistrationOptions, verifyRegistrationResponse,
  generateAuthenticationOptions, verifyAuthenticationResponse,
} from '@simplewebauthn/server';

// サーバーで固定・管理する設定。クライアントのHostから生成しない。
const rpID = 'example.com';
const expectedOrigin = 'https://login.example.com';

async function registrationOptions(ctx) {
  // 認証済み利用者をサーバー側で確定し、直近の再認証を確認
  const user = await ctx.requireRecentAuthentication();
  const existing = await db.listActiveCredentials(user.id);
  const options = await generateRegistrationOptions({
    rpName: 'Example Service', rpID,
    userID: user.handleBytes, // 安定したUint8Array
    userName: user.loginName,
    userDisplayName: user.displayName,
    attestationType: 'none',
    authenticatorSelection: {
      residentKey: 'required', userVerification: 'required',
    },
    excludeCredentials: existing.map(c => ({
      id: c.id, transports: c.transports,
    })),
  });
  const transactionId = await txStore.issue({
    challenge: options.challenge, purpose: 'register',
    sessionId: ctx.sessionId, accountId: user.id,
    ttlSeconds: 180, // この設計例の値。要件に合わせる
  });
  return { transactionId, options };
}
server.js / 登録応答の検証・保存の設計例
async function finishRegistration(ctx, body) {
  const user = await ctx.requireRecentAuthentication();
  // takeは期限・操作・セッション・利用者を確認し、原子的に消費する
  const tx = await txStore.take(body.transactionId, {
    purpose: 'register', sessionId: ctx.sessionId, accountId: user.id,
  });
  const result = await verifyRegistrationResponse({
    response: body.response, expectedChallenge: tx.challenge,
    expectedOrigin, expectedRPID: rpID, requireUserVerification: true,
  });
  if (!result.verified || !result.registrationInfo) {
    throw new Error('REGISTRATION_REJECTED');
  }
  const info = result.registrationInfo;
  await db.insertCredentialUnique({
    accountId: tx.accountId,
    ...info.credential, // id / publicKey / counter / transports
    deviceType: info.credentialDeviceType,
    backedUp: info.credentialBackedUp,
  });
  // 監査イベントと通知は、保存との整合性を保証する方式で記録
  return { verified: true };
}
server.js / discoverable認証の設計例
async function authenticationOptions(ctx) {
  const options = await generateAuthenticationOptions({
    rpID, userVerification: 'required', // allowCredentialsは省略
  });
  const transactionId = await txStore.issue({
    challenge: options.challenge, purpose: 'authenticate',
    sessionId: ctx.sessionId, ttlSeconds: 180,
  });
  return { transactionId, options };
}

async function finishAuthentication(ctx, body) {
  const tx = await txStore.take(body.transactionId, {
    purpose: 'authenticate', sessionId: ctx.sessionId,
  });
  // 未検証IDは検索用にだけ使い、本人と断定しない
  const saved = await db.findActiveCredential(body.response.id);
  if (!saved) throw new Error('AUTHENTICATION_REJECTED');
  const account = await db.findActiveAccount(saved.accountId);
  if (!account || body.response.response.userHandle !== account.handleBase64url) {
    throw new Error('AUTHENTICATION_REJECTED');
  }
  const result = await verifyAuthenticationResponse({
    response: body.response, expectedChallenge: tx.challenge,
    expectedOrigin, expectedRPID: rpID,
    requireUserVerification: true,
    credential: {
      id: saved.id, publicKey: saved.publicKeyBytes,
      counter: saved.counter, transports: saved.transports,
    },
  });
  if (!result.verified) throw new Error('AUTHENTICATION_REJECTED');
  // 失効・アカウント状態を再確認し、競合を処理してから確定する
  await db.finalizeAuthentication(saved.id, result.authenticationInfo);
  await sessions.rotateAndBindAccount(ctx, account.id);
  return { verified: true };
}
APIの周囲に必要な処理

入力スキーマ・サイズ制限、CSRF防御、Rate limit、汎用的なエラー応答、例外処理、資格情報の失効との競合制御を実装します。options/verifyはCache-Control: no-storeとし、CookieはSecure・HttpOnly・適切なSameSiteを設定します。ログに応答全文やセッショントークンを残しません。

challengeの扱い

上の例は検証前に取引を消費します。失敗した場合は新しいoptionsを取得します。DB保存やセッション発行の失敗で中途半端な成功表示を返さない設計にします。ログイン名を先に入力する方式では、options発行時のアカウントにも取引を結びつけ、検証時にCredential IDの所有先が一致することを必須とします。

11 / EXISTING SYSTEMS

既存のWebシステムへ組み込む

選択肢向いている状況調査すべき点
既存IdPのパスキー機能SSO・OIDC基盤がすでにある対応プラン、RP ID、復旧、監査、利用者移行
アプリに直接実装認証画面とアカウントDBを自社管理検証ライブラリ、セッション、運用担当、保守
認証専用サービスに分離複数アプリや複数言語で共通化したいトークン検証、信頼境界、可用性、障害時運用

Tomcat / Javaの場合

ブラウザのWebAuthn呼び出しはサーバー言語に依存しません。Java側で保守されているWebAuthn検証ライブラリを採用するか、既存IdPを利用します。Node.jsを必ず追加する必要はありません。このページのNode.js例は、処理の責務を説明するためのものです。

BFF・認証サービスを分ける場合

ブラウザから届いたverified: trueや利用者IDをアプリが信用する構成にはしません。認証サービスが発行した署名付きトークンやサーバー間の信頼された結果を検証し、issuer・audience・有効期限・nonce等を採用プロトコルに従って確認します。OIDC連携では、セッションとCSRF対策も維持します。

Webとネイティブアプリの共用

AndroidのCredential ManagerやAppleのAuthenticationServicesと、Webの認証基盤を組み合わせる場合は、Webドメインとアプリの関連付けを設定します。アプリの識別・署名情報・サーバーが許容するOriginは各プラットフォームの仕様で確認してください。埋め込みWebViewを通常ブラウザと同じ条件とみなさず、実機で検証します。

参照：[10] / [11]

既存セッションを認証器と取り違えない

パスキーはログイン手段です。アプリのセッション継続・ログアウト・権限変更・重要操作の再認証は、引き続きアプリやIdP側で管理します。

12 / LIFECYCLE & RECOVERY

登録後の管理と、復旧の設計

復旧が弱ければ、攻撃者はログイン画面より復旧窓口を狙います。パスキーを失っても利用できることと、他人にアカウントを渡さないことを両立させます。

場面推奨する設計上の対応
初回登録既存アカウントの認証強度を確認して鍵を追加。新規アカウントの確認手順も明示
追加登録再認証の鮮度を要求。追加完了を既存の連絡先へ通知
端末変更同期の可否、別パスキーの登録、必要に応じた旧資格情報の失効を案内
端末紛失他の登録済み手段を優先し、資格情報の失効と既存セッションへの対応を判断
すべての認証手段を失うリスクに応じた本人確認・待機・通知・手動審査の手順を用意
退職・アカウント停止サーバー側で認証とセッションを無効化。鍵が端末に残っても利用不可にする
削除資格情報の所有者確認と再認証。最後の手段を消す際はロックアウトを防ぐ

サーバーでの削除と、端末側の削除は別

RPで資格情報を無効化しても、端末側の一覧からただちに消えるとは限りません。逆に端末から消しても、RPが必ず通知を受けるわけではありません。対応環境ではWebAuthn Signal APIによる整合性支援を検討できますが、サーバーでの失効処理を置き換えるものではありません。

認証済み操作の再確認

メール変更、送金先変更、パスキー追加などは、過去のログインセッションだけで許可しない方針を検討します。再認証のchallengeを対象操作・アカウントに結びつけ、成功後に実行できる範囲と時間を制限します。

最後の1本を失う前に

異なる認証器の追加、同期アカウントの回復準備、復旧コード等を業務に応じて組み合わせます。SMSやメールを唯一の弱い抜け道にしないよう、復旧全体のリスクを評価します。

関連資料：ブートストラッピングと再認証

参照：[1] / [8] / [9]

13 / INTERFACE DESIGN

迷わせない登録・ログイン画面

「パスキー」という言葉の説明だけでなく、どこに保存され、困ったらどうするかを操作の近くに示します。

画面利用者に伝えること避ける設計
登録案内パスワード入力の負担を減らせること、後から登録できること説明のない強制切り替え
ログイン「パスキーでログイン」の明確な操作、ほかの方法への入口顔認証しか使えないような文言
キャンセル・失敗再試行、別端末、別の認証方法の案内キャンセルを即座に不正扱い
管理画面名前・登録日時・最終利用・削除操作推測した端末名を確定情報として表示
復旧できる操作と次の手順、サポートへの導線利用者の責任だけにする説明

Conditional UI / Autofill

対応ブラウザでは、入力欄の候補からパスキーを選べます。入力要素のautocompleteと、条件付きの認証要求を組み合わせます。対応機能を検出し、明示ボタンでの開始と二重に要求しないよう調整します。

HTML / Autofill向け入力欄の例
<label for="username">ユーザー名</label>
<input id="username" name="username"
       autocomplete="username webauthn">

webauthnトークンは最後に指定します。属性だけで認証は始まりません。要求の開始・キャンセル・ページ遷移を管理し、Autofillを使わない利用者にもボタンや代替経路を用意します。

アクセシビリティ

キーボード操作、ラベル、フォーカスの可視化、読み上げ可能なエラー、色だけに依存しない状態表示を確認します。OSの認証ダイアログはサービス側で自由に描き換えるものではないため、前後の説明と復帰後のフォーカスを整えます。

14 / TEST STRATEGY

仮想認証器と実機で、試験を分担する

試験対象を「アプリの検証ロジック」と「本物の端末・プロバイダーの体験」に分けます。仮想認証器だけで同期・紛失復旧・生体認証の操作感まで保証したことにはなりません。

層試すこと期待する結果
サーバー正常系登録・認証・複数資格情報・セッション更新正しいアカウントにだけ紐付く
サーバー異常系challenge改ざん・再使用・期限切れ・操作種別の入れ替えすべて拒否。セッションを発行しない
境界検証Origin / RP ID不一致・署名改ざん・UV不足すべて拒否し、運用用理由コードを記録
アカウント管理別人への鍵追加・失効済み鍵・停止アカウント操作を拒否する
競合同時verify・複数タブ・失効と認証の競合単回使用とアカウントの整合性を維持
ブラウザE2E仮想認証器で登録→ログアウト→再認証保存・認証・画面遷移が連動する
実機主要OS・ブラウザ、同期、別端末、取消、PIN/生体確認対象環境の案内と操作が成立
復旧・運用全手段喪失、問い合わせ、通知、管理者対応復旧基準・監査記録・失効処理が成立

Chrome DevToolsで最初に確認する

  1. 検証環境を開き、DevToolsのWebAuthnパネルを表示します。
  2. 仮想認証器を追加し、CTAP2・resident key・user verification等を試験要件に合わせます。
  3. 登録し、Credential ID・User Handle・Sign Countを確認します。
  4. ログアウト後に認証し、無効化した資格情報では拒否されることを確認します。

Playwrightでの自動化の入口

Chromium向けのChrome DevTools Protocol（CDP）を使う準備例です。WebKit共通のコードではありません。対象アプリのURL・操作・期待値を加えて、実際のサーバー検証まで通してください。

      hasResidentKey: true, hasUserVerification: true,
      isUserVerified: true, automaticPresenceSimulation: true,

    // この位置に自社アプリの登録→ログアウト→再認証を追加

16 / DELIVERY

小さく導入し、測定しながら広げる

段階決めること次へ進む条件の例
現状調査利用者層、認証基盤、対象端末、リスク対象サービス・責任者・復旧方針が決まった
設計・試作RP ID、UX、DB、取引管理、検証処理主要な正常系と拒否ケースを説明できる
限定提供少人数・限定環境で登録と利用成功率と問い合わせ、復旧訓練を評価できた
展開案内改善・サポート・監視利用環境別の失敗を把握し対処できる
既存方式の整理パスワード等を残す条件・縮小計画ロックアウト防止と安全性の基準に合意できた

数字の分母をそろえる

登録率は「対象利用者のうち登録した割合」、認証成功率は「試行のうち成功した割合」など、定義を決めます。OS・ブラウザ・認証方式ごとに集計し、取消と技術的な失敗も分けます。利用者属性の違いを無視して、パスキー利用者と全利用者を単純比較しないでください。

運用指標

  • 登録開始→登録完了、認証開始→サーバー成功の率と所要時間
  • 対象利用者あたりの問い合わせ・復旧申請・不正な資格情報追加
  • 既存方式へのフォールバック率と、弱い経路が残る範囲
  • 外部IdPや依存ライブラリの更新時に再確認する試験と担当者

この導入手順・評価指標は本ガイドの設計提案です。特定の削減率や導入期間を保証するものではありません。
